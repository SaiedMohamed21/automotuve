PHASE 3 — IMPLEMENTATION REPORT: Cross-Session Data Synchronization
================================================================================

We have completed Phase 3 successfully.
Cross-session / cross-tab stale data has been eliminated by implementing ASP.NET Core SignalR push notifications + automated client API data refetching. 

When any user/session creates or modifies business data in SQL Server (Job Orders, Parts, Invoices, Payments, Customers, Vehicles, Suppliers, Expenses, Payroll), all other authenticated open sessions across all roles receive real-time invalidation notifications and refresh their data automatically without requiring manual F5.

--------------------------------------------------------------------------------
A. ROOT CAUSE OF CROSS-SESSION STALE DATA
--------------------------------------------------------------------------------
Previously, the application maintained business state in React local state (App.tsx) and fetched data from REST APIs only on initial page load / post-login. There was no real-time push mechanism or event listener to notify open tabs when another user saved a mutation to SQL Server. Users had to manually refresh the browser (F5) to see changes made by other sessions.

--------------------------------------------------------------------------------
B. SYNCHRONIZATION TECHNOLOGY SELECTED
--------------------------------------------------------------------------------
ASP.NET Core SignalR (`Hubs/DataSyncHub.cs` on `/hubs/sync`) + `@microsoft/signalr` client in React.

--------------------------------------------------------------------------------
C. WHY SIGNALR WAS SELECTED
--------------------------------------------------------------------------------
1. Built-in to ASP.NET Core .NET 8 (zero extra NuGet dependencies).
2. Native WebSockets support with automatic fallback to Long Polling on Azure App Service.
3. Lightweight: Sends tiny 20-byte event notifications (`DataChanged`, `category`) without pushing large payloads.
4. Preserves Backend Role Authorization: Receiving clients trigger existing authenticated REST API calls (`loadBackendData()`), ensuring each role receives only data they are authorized to access.
5. Reconnection & Resilience: `withAutomaticReconnect([0, 2000, 5000, 10000, 30000])` recovers automatically from tab sleep, network drops, and server restarts.

--------------------------------------------------------------------------------
F. NEW ENDPOINTS / HUBS / EVENTS
--------------------------------------------------------------------------------
- Endpoint: /hubs/sync (SignalR Hub Endpoint)
- Server Event: DataChanged (Payload: category string e.g. "JobOrders", "Parts", "Invoices", "Customers", "Vehicles", "All")

--------------------------------------------------------------------------------
G. HOW AUTHENTICATION IS HANDLED
--------------------------------------------------------------------------------
- SignalR connection passes JWT bearer token in query parameter `?access_token=...`.
- Program.cs JwtBearerEvents extracts token for `/hubs` requests.
- SignalR client connects only when user is authenticated.
- Logout (`selectedRole == null`) calls `stopSignalRSync()` and closes the connection.
- Refetch requests triggered by notifications pass through existing JWT authenticated REST APIs.

--------------------------------------------------------------------------------
H. WHICH DATA-CHANGE EVENTS ARE SYNCHRONIZED
--------------------------------------------------------------------------------
- Job Orders: Create Job Order, Update Job Order, Update Status, Save Work Found, Confirm Issue
- Parts: Create Part, Update Prices, Issue Parts, Confirm Issue, Update Stock Count
- Invoices & Payments: Create Invoice, Record Payment
- Customers: Create Customer, Update Customer
- Vehicles: Create Vehicle, Change Owner
- Suppliers & Purchases: Create Supplier, Purchase, Receive Stock, Record Payment
- Expenses: Create Expense, Void Expense
- Payroll: Attendance, Transactions, Technician updates

--------------------------------------------------------------------------------
I. HOW FRONTEND REACTS TO EVENTS
--------------------------------------------------------------------------------
When `DataChanged` is received from SignalR, the frontend executes `loadBackendData()`, which refetches fresh data from the backend REST APIs for the user's role and updates React state.

--------------------------------------------------------------------------------
J. HOW DUPLICATE REFRESHES ARE PREVENTED
--------------------------------------------------------------------------------
1. SignalR Service Debouncing: 300ms timer coalesces rapid consecutive events into a single refresh.
2. Phase 1 Protection: `isDataLoadingRef` and `setIsBackendLoading` prevent concurrent duplicate executions of `loadBackendData()`.

--------------------------------------------------------------------------------
K. HOW RECONNECT / RECOVERY WORKS
--------------------------------------------------------------------------------
- Client configured with `.withAutomaticReconnect([0, 2000, 5000, 10000, 30000])`.
- On reconnection (`onreconnected`), client triggers a catch-up data sync (`loadBackendData()`) to pick up any changes that occurred while offline.
