A. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
This forensic investigation analyzed the reported data consistency, role visibility, parts availability, and cross-screen synchronization issues in the SOS Motor Works application.

The investigation confirms that while the application relies on a single, unified database schema managed by Entity Framework Core, the reported symptoms stem from three distinct architectural root causes working in combination:

1. Authorization Role Mismatch (Parts Inconsistency): The primary Parts endpoint (GET /api/warehouse/parts) is annotated with [Authorize(Roles = "Warehouse,Owner,Engineer")]. Accountant users are explicitly excluded from accessing this endpoint, resulting in HTTP 403 Forbidden responses. Because the frontend initial data load (loadBackendData) queries api.getParts() for all users on startup, logins by Accountant users cause the initial Parts Promise to reject, leaving the frontend state empty or reliant on local fallback data.

2. Missing Real-Time / Inter-Session Synchronization Architecture: The React SPA manages application state in monolithic useState hooks loaded once on startup (useEffect on mount). When a Job Order or Part is created/updated in one browser tab, the mutation updates the backend database and the local React state of that specific browser session only. There is no WebSockets/SignalR, Server-Sent Events, polling, or cross-session cache invalidation. Consequently, already-open screens in other browser tabs/roles retain stale snapshots until a manual browser refresh (F5) is performed.

3. Identity-to-Entity Decoupling (Engineer Visibility): The JobOrder model stores the engineer reference as a plain, unconstrained string property (public string? Engineer { get; set; }) populated from User.Identity.Name during creation. There is no foreign key linking JobOrder to ApplicationUser or an Engineer entity. If username/email representations differ between JWT tokens or seeding, or if the initial API request fails during login/navigation, Job Orders appear missing for Engineer users.

Q. FRONTEND SYNCHRONIZATION ARCHITECTURE
--------------------------------------------------------------------------------
- Initial Load: Handled by loadBackendData() in useEffect([], ...) in src/App.tsx on component mount.
- Mutation Behavior: When a user creates or updates a Job Order or Part:
  1. An HTTP POST/PUT is sent to the backend API.
  2. The local React state in that specific tab/session is updated via setJobOrders((prev) => [newJO, ...prev]).
  3. No refetch signal or push notification is sent to other active browser tabs or sessions.
- Synchronization Failure Cause: Because there are no WebSockets (SignalR), no SSE, no periodic background polling, and no cross-session invalidation, screens already open in other browser sessions retain stale state until the user reloads the browser (F5).

S. DATABASE DATA INTEGRITY FINDINGS
--------------------------------------------------------------------------------
1. Soft Delete Cascades: Customer and Vehicle use soft delete (IsDeleted = 1). JobOrders do not use soft delete. If a Customer or Vehicle is soft-deleted, their historical JobOrders remain intact in JobOrders table, but querying through EF Core with query filters hides the parent Customer or Vehicle unless explicitly configured.
2. Unconstrained Engineer Name: JobOrder.Engineer is stored as plain text. If an engineer's full name is altered in AspNetUsers, existing JobOrders retain the old string name.
3. Inventory Movement Audit: Stock movements correctly record quantity additions (StockIn) and deductions (Issue), maintaining an audit log alongside Part.CurrentQty.

U. CONFIRMED ROOT CAUSES
--------------------------------------------------------------------------------
1. Accountant 403 on Parts (Problem 2 Root Cause): [Authorize(Roles = "Warehouse,Owner,Engineer")] on WarehouseController excludes Accountant. api.getParts() fails for Accountant users on startup.
2. Lack of Cross-Tab / Cross-Session Synchronization (Problem 3 Root Cause): Data is fetched ONCE on component mount. Local state mutations do not trigger refetches or WebSocket updates in other active sessions.
3. Role-Specific Job Order Filtering & Endpoint Divergence (Problem 1 Root Cause): Warehouse queries /api/warehouse/jobs (filtered to Open), Accountant queries /api/accountant/jobs, and Engineer queries /api/job-orders. If the initial GET /api/job-orders call fails during login/token initialization, local React state defaults to empty.


--------------------------------------------------------------------------------
V. LIKELY ROOT CAUSES
--------------------------------------------------------------------------------
1. JWT Claim Mismatch during Initial Load: If an Engineer logs in and loadBackendData() executes before the token is properly attached to localStorage, the initial Promise.allSettled request returns 401 Unauthorized, leaving jobOrders state unpopulated until manual page refresh.

X. ISSUES THAT ARE RELATED
--------------------------------------------------------------------------------
- Parts Inconsistency & Role Authorization: The intermittent disappearance of Parts is directly linked to whether the logged-in user role is permitted to call GET /api/warehouse/parts.
- Job Order Visibility & Initial API Load Rejection: Missing job orders for Engineers occur when token initialization delays cause the initial api.getJobOrders() request to reject on startup.

Y. ISSUES THAT ARE INDEPENDENT
--------------------------------------------------------------------------------
- Cross-Screen Synchronization: The requirement for browser refresh (F5) to see newly created records across different open sessions is an architectural frontend/real-time state limitation, independent of role authorization filters or SQL Server database queries.


--------------------------------------------------------------------------------
Z. RECOMMENDED FIX PLAN (For Reference Only — No Changes Made)
--------------------------------------------------------------------------------
1. Role Authorization Fix:
   - Update [Authorize(Roles = "Warehouse,Owner,Engineer,Accountant")] on WarehouseController or create a dedicated shared endpoint for Parts reading so Accountant users can access inventory data without receiving 403 errors.
2. Synchronization Fix:
   - Introduce light polling (e.g. interval-based refetch in active windows) or ASP.NET Core SignalR hub notifications so mutations broadcast cache invalidation events to active browser tabs.
3. Engineer Association Fix:
   - Standardize engineer identification by adding an explicit EngineerId reference linked to ApplicationUser.Id while maintaining backward compatibility with existing string fields.
